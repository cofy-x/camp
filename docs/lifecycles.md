# Camp lifecycle map

The [team workflow](workflow.md) starts in Discussion or Work and ends with a result or an explicit decision. A matter, its finite collaborations, their Runs, and any external delivery can advance independently. The [architecture](architecture.md) owns their authority and persistence contracts. This map locates the transitions whose effective state depends on more than the stored status.

Keep one owner for each transition. Derive current presentation from that owner's facts, including the current actor, related identity, version and outstanding effect. Use named states or a small pure selector where the combination changes what the user can do. Agents propose decisions using the frozen instructions and evidence. Storage validates those decisions and the actions shown in the browser against current authority.

Use the existing lifecycle and request identity when extending recovery. An unanswered question in history stays readable; only a current question can receive an answer. A dispatched effect can remain unconfirmed after its authority expires or is withdrawn. Keep its receipt recoverable and recheck authority before any later write. Follow the existing [UI](design.md#review-checklist), [API](api.md) and [performance](performance.md) contracts when testing these boundaries.

## Durable product state

| Lifecycle | Owner | State that needs more than a label |
| --- | --- | --- |
| Team setup, invitations and sessions | [Team storage](../apps/server/internal/storage/team.go), [authentication API](../apps/server/internal/httpapi/auth.go) | Setup and invitation consumption precede an authenticated session. Expiry, account disable and revocation can change current access to retained data and work. |
| Room message and explicit execution | [Room admission policy](../apps/server/internal/orchestration/policy.go), [message transaction](../apps/server/internal/storage/room_messages.go) | Recipient selection and Post only determine whether an immutable message also admits a Run or supplies subscribed context. Readiness is a preflight; the committed receipt determines the admitted work. |
| External observations | [GitHub ingress](../apps/server/internal/githubhooks), [Feishu ingress](../apps/server/internal/feishuhooks), [source event storage](../apps/server/internal/storage/automation_events.go) | Current source revision and actor identity admit a deduplicated original. Its processing/decision state is separate from the original and from source enablement. |
| Rule, context subscription and assessment | [Automation storage](../apps/server/internal/storage/automation.go), [evaluation claims](../apps/server/internal/storage/automation_evaluations.go) | Enabled mode, intake frontier, subscription, charged daily slot and frozen candidate jointly determine whether later events are context, observed, assessed or admitted. A late result rechecks the current frontier. |
| Project defaults and delivery grant | [Project settings](../apps/server/internal/storage/project.go), [delivery authority](../apps/server/internal/storage/github_repair.go) | A saved personal preset proposes values. Delivery from a rule needs its own current project and rule revisions. A save, read or revoked proposal changes no existing receipt. |
| Matter and current execution | [Work commands](../apps/server/internal/storage/work_items.go), [task-to-Work synchronization](../apps/server/internal/storage/work_flow.go) | Stop intent, active task identity, question, retained results, allowance and expiry give the matter its current meaning. A latest historical task can be present without being active. |
| Follow-up and expiry | [Timers](../apps/server/internal/storage/work_flow.go), [expiry](../apps/server/internal/storage/work_deadlines.go) | A scheduled timer, a business due date and expiring execution authority have different consequences. Firing, replacing or cancelling a timer commits with its owner and evidence. |
| Completing a matter | [Completion judgment](../apps/server/internal/storage/work_completion.go), [effect gate](../apps/server/internal/storage/work_actions.go) | The task result, current approval or criteria, evidence frontier and confirmed effects determine completion. An awaiting receipt can outlive the proposal that would have closed the matter. |
| Room uploads and Runner imports | [Upload receipts](../apps/server/internal/storage/room_uploads.go), [Runner capture](../apps/server/internal/storage/remote_sources.go) | A stored original is available to reference before it is attached to a message. A capture requires current Runner/lease, verified bytes and a committed import receipt before its Room files become usable. |
| Editing and publishing Room files | [Library](../apps/server/internal/storage/library.go), [writer leases](../apps/server/internal/storage/remote_leases.go), [task execution](../apps/server/internal/storage/task_execution.go) | Private edits, a team task checkpoint and the shared Resource pointer are independent. Publication, copy and restore keep exact source versions and check the current shared baseline. |
| Shared memory | [Memory revisions](../apps/server/internal/storage/memories.go) | Current active/retracted metadata controls future retrieval. An assessment retains the exact revisions it read. Memory can provide context without changing execution authority. |
| Human review | [Review commands](../apps/server/internal/storage/reviews.go) | A current review depends on its pinned shared version, assigned enabled reviewer and recorded decision. Outdated work and a missing reviewer require different recovery; delivery retains the approved version. |
| GitHub comments | [Comment delivery](../apps/server/internal/storage/automation_deliveries.go) | Withdrawal, recorded attempts and confirmed comment IDs remain separate facts. An obsolete question withdraws future sends while an earlier unconfirmed POST remains checkable. |
| GitHub code delivery and repair | [Claim and receipt storage](../apps/server/internal/storage/github_delivery.go), [provider steps](../apps/server/internal/githubdelivery/client.go) | Stage, claim lease and receipt certainty determine dispatch or read-only checking. Current scope controls future writes. Known feedback can admit one finite repair under the existing Work and source grant. |
| Personal attention and reads | [Attention projection](../apps/server/internal/storage/attention.go), [personal reads and Inbox](../apps/server/internal/storage/team_personal.go) | Current responsibility comes from Work, Task, Review and Delivery. Notification position and unread styling can change independently; they cannot resolve responsibility. |

## Execution and process state

| Lifecycle | Owner | State that needs more than a label |
| --- | --- | --- |
| Runtime setup and process ownership | [Launcher](../internal/launcher/entrypoint.go), [Server](../apps/server/internal/server/server.go), [Runner status](../apps/server/internal/daemon/status.go) | Installed package and runtime, live process, ownership lock and data compatibility are separate. Restart must retain machine and data identities and settle claims by their journal. |
| Configured model and execution readiness | [Configuration](../apps/server/internal/configuration), [Runner and Agent grants](../apps/server/internal/storage/remote_runners.go), [model admission](../apps/server/internal/remoteruns/model.go) | Connection, readiness, current access, frozen model configuration and remaining allowance are distinct. The selected Runner can be reachable without admitting a particular Run. |
| Collaboration and input coverage | [Task commands](../apps/server/internal/storage/tasks.go), [round decisions](../apps/server/internal/storage/task_policy.go), [input history](../apps/server/internal/storage/task_inputs.go) | The goal, current round, input frontier, question and checkpoint advance separately. Only accepted results extend covered input; late inputs and yielded decisions may need a subsequent round. |
| Run preparation, Attempt and writer fence | [Preparation worker](../apps/server/internal/remoteruns/preparation_worker.go), [Attempt storage](../apps/server/internal/storage/remote_attempts.go) | A queued Run, an unsent prepared command, an executing lease and accepted upload have different recovery. Connection epochs and lease/fence checks constrain execution and publication independently. |
| Runner command, events and result | [Daemon journal](../apps/server/internal/daemon/journal.go), [transfer](../apps/server/internal/daemon/transfer.go), [result acceptance](../apps/server/internal/remoteruns/results.go) | Durable acceptance, acknowledgement, output sequences, upload and final receipt need separate identities. Duplicate transport may recover the original receipt. Terminal intent and confirmed cleanup decide whether a slot can be reused. |
| Model and native workspace session | [Native executor](../apps/server/internal/nativeexecutor/executor.go), [coordination](../apps/server/internal/nativeexecutor/coordination.go), [DSH](dsh.md) | Resume depends on a previously accepted shutdown, matching runtime/session identity and current scope. A proposed handoff or finish must be sealed and drained before the Server can accept it. |
| Run activity and frozen inspection | [Output ingestion](../apps/server/internal/storage/run_output.go), [activity reads](../apps/server/internal/storage/run_activity.go) | A growing output tail and the business result have separate lifetimes. An inspection window can retain its read frontier while execution and output advance. |
| Native checkpoint and stopped storage maintenance | [Checkpoint worker](layerfs-worker.md#sealing-receipts-and-recovery), [Server maintenance](../apps/server/internal/serverstorage/maintenance.go) | Capture, independent readback, acceptance and cleanup need their own proof. Quarantine, restore and purge use explicit plans and preserve referenced results and their identities. |

## Account and browser state

| Lifecycle | Owner | State that needs more than a label |
| --- | --- | --- |
| Sign-in and desktop bootstrap | [Auth gate](../apps/dashboard/src/team/AuthGate.tsx), [bootstrap](../apps/dashboard/src/app/useBootstrap.ts) | Loading, setup, invitation, offline recovery and the accepted account/desktop generation do different work. Signing out flushes retained drafts first. |
| Live reads and connection | [Team provider](../apps/dashboard/src/team/TeamContext.tsx), [read store](../apps/dashboard/src/shared/reads/store.ts) | Durable event cursor, in-flight/dirty reads, accepted snapshots, revocation and hidden-window suspension are independent. Reconnection revalidates without losing an intentional page or draft. |
| Private draft and submit recovery | [Private draft](../apps/dashboard/src/team/usePrivateDraft.ts), [recorded operations](../apps/dashboard/src/shared/useRecordedOperation.tsx), [Work request owner](../apps/dashboard/src/features/workitems/useWorkItemOperation.tsx) | Load, local edits, revision conflicts, confirmed writes, missing/unknown receipts and cancellation tombstones are distinct. Recorded Work creation can still be waiting for private draft cleanup. |
| Discussion composer and attachments | [Conversation intent](../apps/dashboard/src/features/workspace/conversationState.ts), [upload store](../apps/dashboard/src/features/workspace/uploadState.ts) | Recipient, Room/Thread, unsent files, frozen send body and later edits retain separate scope. A delayed receipt can clear only the draft it confirms. |
| Workspace, Work and Library navigation | [Workspace view](../apps/dashboard/src/features/workspace/useWorkspaceView.ts), [Work controller](../apps/dashboard/src/features/workitems/useWorkController.ts), [Library view](../apps/dashboard/src/features/library/useLibraryView.ts) | Room and scope, inspection return paths and window activation revision govern asynchronous navigation after draft saves. A late save cannot switch windows. |
| Work creation and current response | [Creation draft](../apps/dashboard/src/features/workitems/creationDraft.ts), [current question](../apps/dashboard/src/features/workitems/presentation.ts), [Work action draft](../apps/dashboard/src/features/workitems/workActionDraft.ts) | Freeze the selected defaults and submitted grant with the draft. Visible progress and answer controls follow the current task/question, while a private answer retains its original revision until reviewed. |
| Library selection and environment | [Library controller](../apps/dashboard/src/features/library/useLibraryController.ts), [environment snapshot](../apps/dashboard/src/features/library/environmentState.ts), [import receipt](../apps/dashboard/src/features/library/sourceImportState.ts) | Accepted sources, selected commit, editing, comparison and optional environment changes have different baselines. Leaving or changing a selection cannot acknowledge a different save. |
| Inspection lists and review decisions | [Run inspection](../apps/dashboard/src/features/workspace/useRunInspector.ts), [Work history](../apps/dashboard/src/features/workitems/WorkItemHistory.tsx), [review panel](../apps/dashboard/src/features/reviews/ReviewPanel.tsx) | Accepted page, pending navigation, new records, retained comment and current decision revision can move separately. History reads and focus changes do not submit decisions. |
| Getting Ready and Runner verification | [Readiness](../apps/dashboard/src/features/settings/useReadiness.ts), [sample receipt](../apps/dashboard/src/features/runners/useFirstTask.ts) | Agent work availability, recorded native results and a sample request each have their own evidence. Recover a pending sample using its original request identity. |
| Desktop, overlays and preferences | [Desktop controller](../packages/platinum/src/desktop/useDesktopController.ts), [gestures](../packages/platinum/src/desktop/useDesktopGestures.ts), [overlays](../packages/platinum/src/overlays.tsx), [layout persistence](../apps/dashboard/src/app/layout-persistence.ts) | Open, foreground, shaded, provisional pointer and committed layout state differ. Menu/dialog lifetime and focus restoration stay local to the desktop. Persisting layout or preferences has no business effect. |
