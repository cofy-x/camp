# GitHub integration

A Room can receive GitHub repository webhooks. By default, deliveries create immutable observations awaiting a teammate's decision. Reading, refreshing and configuring a source make no model request. A teammate can choose a goal and approved Room Agents in **Start collaboration…**, or an administrator can explicitly delegate future work through [Automation](#automated-work-and-replies). The [task authority and publication contract](architecture.md#collaboration-tasks) remains authoritative.

## Connect a repository

1. As an administrator, open the Room's **More → Sources & rules…** and choose **Connect GitHub…**. For a Room with configured sources, expand **GitHub sources**.
2. Add `owner/repository` and a random webhook secret of 32–256 bytes. Events and original payloads will be visible to every enabled team member, like the Room.
3. Open **Webhook setup** and copy the Payload URL into that repository's GitHub Webhooks settings. Select `application/json`, enter the same secret, retain SSL verification and subscribe to **Issues**, **Pull requests** and **Issue comments**.
4. Use an externally reachable HTTPS Camp origin. Loopback HTTP is supported only for local protocol checks; this feature does not create a tunnel or configure GitHub, DNS, certificates or background services.

Camp verifies `X-Hub-Signature-256` against the exact body using HMAC-SHA256 and a constant-time comparison, following [GitHub's signature contract](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries). This endpoint accepts no member Cookie, browser Origin or Authorization header. The ordinary team APIs retain session and Origin protection. The [API contract](api.md#github-observation) owns request and response details.

Sources are fixed to a Room and repository name. The first valid delivery pins the repository's numeric identity; later deliveries must match both. A rename, transfer or replacement needs a new explicitly configured source. Disable the old source to retain its events and decisions. The same address can then have a replacement source, including after repository deletion/recreation. Only one source for that Room/address can be enabled at a time; re-enabling an older source requires disabling its replacement first. Repository IDs distinguish their histories. A Room supports up to 32 retained sources.

Clearing **Enabled** stops new deliveries and confirmations, including pending events. It preserves observations, receipts and already authorized tasks; use a task's own cancellation controls to stop that work. Rotating a secret immediately rejects deliveries verified with the old credential, including an ingress request that raced the rotation. Update the repository's webhook secret separately.

Select the repository in **Sources & rules** and choose **Verify saved setup**. The check reads the newest signed original for the current source revision, the saved rule and its Runner access. If the receipt is missing, send a fresh ping or supported event from GitHub and check again. Redelivering an original from an earlier revision keeps that original's receipt. The check previews intake of a recent supported event using the saved rule's sender and revision gates. A passing sample is eligible for assessment. The Agent applies the rule instructions during assessment. The rule owner also sees the effective delivery scope and saved CI workflow. These are local configuration and receipt checks. Current GitHub access, Runner connectivity and CI success are confirmed separately during execution and delivery.

## Decide an event

Open **Automation → Activity → GitHub inbox** for events awaiting manual confirmation. **All events** includes accepted, dismissed and ignored observations. Opening an event shows its subject, external actor, original text and next action. **Event details** holds transport metadata and the original JSON download. GitHub identities are never mapped to Camp members. Bot, unresolved/ghost and unsupported events remain recorded as ignored observations.

The supported candidate actions are:

| Event | Actions |
| --- | --- |
| `issues` | `opened`, `reopened`, `edited` |
| `pull_request` | `opened`, `reopened`, `edited`, `synchronize`, `ready_for_review`, `closed` |
| `issue_comment` | `created`, `edited`, including PR issue comments |

Other event/action combinations and connection pings are recorded as ignored. Use [source recovery](#reconcile-missed-deliveries) for a suspected delivery gap. Webhook setup itself grants no GitHub API credential, repository checkout or external reply permission.

**Start collaboration…** prepares an editable goal. It starts nothing until the teammate selects participants and submits the existing finite task authorization. The complete normalized event is copied into the task's append-only input log in UTF-8 chunks, labelled as untrusted external context supplied by the confirming member. Chunk wrappers preserve the authored body's whitespace. The task freezes the accepted input frontier and records its source event ID. Source context uses input protocol 1 and summary responses so large originals remain page-readable. The original webhook bytes are retained independently, without backfilling older tasks or changing their request hashes.

Confirmation writes the event decision, task, inputs, first queued Run, admission journal and task receipt in one SQLite transaction. One event can have one final human decision. Concurrent confirmations cannot create a second task, and an exact request replay returns its original task even after the source, model or route changes. Dismissal records the member, time and required reason without starting work. Event text cannot select Agents, expand budgets or resume work.

## Delivery, recovery and private state

The Server acknowledges a webhook only after its observation and delivery receipt commit. The delivery GUID is unique within its source; changed content under the same GUID conflicts. Byte-identical redeliveries are also deduplicated when their GUID changes. Ordering uses committed local sequences, rather than external timestamps. Reads use bounded pages and a frozen event frontier; decision states on those immutable events remain current.

After an uncertain task start, retain its exact request body and ID and use **Retry Start**, or open the event's recorded collaboration. Configuration and dismissal retain a private per-user receipt. **Check Saved Operation** reads that receipt without sending another write. Browser recovery stores only the operation ID for source settings; it never stores a webhook secret. Clearing an unresolved configuration recovery does not cancel an in-flight write. Expected revisions, source uniqueness and immutable event decisions still protect subsequent writes.

Raw deliveries are limited to 1 MiB, candidate titles to 1024 UTF-8 bytes and bodies to 64 KiB. Oversized/malformed deliveries fail explicitly; originals are never silently truncated. Credentials live in owner-only immutable files under `configuration/github-webhooks` in Server's data directory. SQLite stores opaque references and request hashes, never secret text. A file persisted before a failed database write can remain unreferenced; it cannot activate a source and is not automatically purged. Back up the complete stopped Server directory as described in [installation](install.md#data-upgrades-and-backup).

### Reconcile missed deliveries

An administrator can compare one active repository hook's latest 100 GitHub delivery attempts with Camp receipts. The command verifies the pinned repository ID and exact HTTPS callback. Use a Camp administrator access file in the [operator format](dsh.md#real-provider-verification) and a separately configured `gh` identity with repository Webhooks read access. The report includes the oldest observed attempt and whether the page limit was reached. An empty report describes only the sampled provider window. [GitHub delivery history](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/viewing-webhook-deliveries)

```sh
node scripts/reconcile-github-source.mjs CAMP_ORIGIN ACCESS_JSON ROOM_ID SOURCE_ID HOOK_ID PUBLIC_ORIGIN
```

A Camp event ID confirms the signed original was committed. A sampled GitHub success for a GUID without a Camp receipt warrants checking the endpoint and data directory. For a failed attempt without a receipt, repeat the command with `--recover DELIVERY_ID` and separately authorized Webhooks write access. The command prepares one GUID in Camp, asks GitHub to redeliver it once, then checks the exact receipt. It reports an unconfirmed dispatch as awaiting the receipt. A repeated command can read an existing preparation or receipt. If a prepared attempt still needs a redelivery, inspect the hook's delivery history before explicitly redelivering it from GitHub.

The original must pass normal signature, source and repository checks. Registered historical deliveries appear as **Recovered event** in Activity. Camp preserves these events as evidence for explicit review. Existing receipts take precedence. The operator command samples the recent delivery history available through GitHub. [GitHub redelivery](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks)

## Automated work and replies

Open the Room's **More → Activity…** to see recent events first. Source filtering applies before pagination; older pages keep their original intake frontier until **Refresh Events** opens the latest range. Each row shows its source, author, text preview and recorded outcome. **Open Work** goes directly to the related matter and its delivery status. **Details → Assessment decision** retains the frozen rules, proposed goal, reason and related tasks; **Event data** holds technical identifiers and the original payload download.

Open **Sources & rules** and select the GitHub source to configure its policy. New policies are **Off**. Choose **Observe** or **Auto**, rules, allowed numeric GitHub actor IDs, approved Room Agents and finite task/daily allowances, then explicitly save. Participant selection expands when needed; a single participant is automatically first. The allowance summary stays visible while its numeric controls are under **Adjust allowance**. **Observe** assesses new eligible events using a model and records its result without starting work. **Auto** authorizes new finite collaborations under that delegation. Saving or reading settings makes no model request; enabling a policy applies only to future intake, never earlier observations. Each edit has a revision and new intake frontier. The [automation API](api.md#event-automation) owns limits and [bounded assessment](dsh.md#event-assessment) owns model behavior.

The same source Thread can supply context to several active tasks. Expand an event in **Automation**, choose **Follow in Collaboration…** and select an active task you manage. This starts no work. **Task setup → Conversation tracking** shows and controls existing subscriptions. New discussion is context under the existing grant; it does not resume finished work, increase allowances or implicitly answer a question. Room **Post only** also bypasses automatic work and subscription delivery. External actor attribution remains separate from Camp users. Existing explicit Agent requests keep their ordinary Run behavior.

Enable **Allow answers to task questions** only when listed GitHub participants may answer a task's current question. The exact command is `/camp answer <questionId> <answer>`, posted in its followed conversation by an allowed human actor. A matching unanswered question can continue within the task's remaining allowance. Stale, ambiguous and invalid commands start nothing. Ordinary comments supply context and are independently considered for new work.

To send ordinary issue/PR conversation comments, enable **Post task questions and results as GitHub comments**, save the policy and configure its separate **Comment credential**. Use a repository-restricted token and the numeric ID of its GitHub account. Credentials stay in owner-only Server files and never enter tools, task inputs, returned configuration, browser recovery or logs. This permission covers structured questions, actionable failures and final results; it grants no inline review replies, pull-request creation, pushes or merges.

Task setup shows each outgoing comment's frozen body, destination and delivery state. A lost POST response is **Delivery not confirmed**, followed by one read-only reconciliation. **Check GitHub Delivery** searches for the exact marker, body and recorded dispatch actors, including earlier accounts after credential rotation. Missing or incomplete evidence leaves delivery unknown. **Resend Comment…** explicitly permits another send and warns that a duplicate is possible; absence is never presented as proof of non-delivery. Known failed or blocked deliveries offer **Retry Comment** after repair. Obsolete questions and cancelled tasks withdraw queued sends and offer no resend; an earlier unknown outcome remains visible and can still be checked read-only. Withdrawn old questions stop blocking later task notices. **Delivery details** retains dispatch outcomes and confirmed comment links, with an explicit indication when a bounded scan may omit other matching comments. A delivery allows at most 32 dispatch attempts. Restart turns interrupted dispatch outcomes into unknown and reconciles without automatically posting again. Current source, task authority, comment permission and credential are rechecked before dispatch. Exact Camp output remains excluded from new automatic requests across sources observing the same repository discussion.

Policy drafts remain private and survive navigation. A newer saved revision offers **Keep My Edits** or **Reload Saved Policy**; keeping edits only changes the baseline and never saves automatically. Credential edits also retain their original policy revision until **Use Current Policy** explicitly accepts a newer baseline. Uncertain policy, credential, subscription and delivery commands retain their request ID for **Check Saved Operation**. If no receipt exists, **Cancel Unconfirmed Operation** either recovers a concurrently committed result or records a cancellation that rejects any late original write. Drafts stay intact; the UI never merely forgets the pending ID. Credential text stays only in the mounted form and is never stored in browser recovery. Save it or explicitly choose **Clear Credential Edits** before switching sources or leaving; uncertain submitted requests keep their separate receipt recovery. The [remaining event boundaries](architecture.md#current-implementation-limits) include missed-history polling and arbitrary external actions; [Feishu ingress](feishu.md) has its own authenticated adapter.

## Authorized code delivery

A personal **Settings → GitHub** connection lets Work deliver an accepted source change without giving an Agent a GitHub token or asking a person to perform each step. Connect `owner/repository` with a repository-restricted token, a required CI workflow filename for automatic merging, and an optional deployment workflow. The Server verifies the authenticated account, numeric repository identity and repository role. The token still needs **Contents** and **Pull requests** write access and **Actions** read access; GitHub enforces its actual permissions on each request. Connection metadata and drafts are private to their owner. Credentials live in immutable owner-only files under `configuration/github-delivery`, outside SQLite, browser storage, Agent inputs and Runner environments.

In **New work → Options → Delivery**, choose the repository, target branch and **Open a pull request**, **Merge after CI**, or **Merge and publish a release**. Release mode accepts an exact tag or the accepted root `package.json` version within an explicitly approved `major.minor` release line; deployment waiting is optional. The resolved tag is checked before any visible publication. The destination, public/private visibility and permitted effects stay visible when Options closes. Delivery requires explicit authorization and automatic Work completion. Personal **Work → More → Project settings…** can propose Agents, total allowance, completion and destination for later Work. Saving defaults starts nothing. An enabled automatic rule can inherit delivery only through its owner’s separate project grant, tied to the exact rule and project revisions. Its source, participants, per-task and daily caps remain authoritative; defaults never widen them. An inbound webhook or an ordinary-comment policy alone grants no publishing permissions. New Work does not load connection settings until delivery options are opened or a saved delivery choice needs validation.

Authorization freezes the Room's source baseline, repository identity and visibility, GitHub account, target branch, CI/deployment workflow identities and release scope. Only the finite task's accepted completion judgment, after publication to the Room, can activate delivery. The Server compares that baseline with the immutable accepted result, reads changed blobs in a batch, and overlays only those changed paths on the remote base tree. The accepted project’s `.gitignore` rules exclude newly generated/ignored paths, using Git’s own matcher; files already tracked in the destination remain tracked. Source selection is versioned with the authorization, and original Room artifacts stay intact. It rejects changed remote baselines for affected files, unsafe paths, GitHub configuration edits and source patches exceeding 128 changed files or 8 MiB. Unmanaged files, including existing CI workflows and provenance, remain in the remote tree. The initial visible-effect reservation is two actions for branch/PR, three through merge, or four through release.

A durable queue progresses through immutable Git object preparation, a unique non-forced branch, a marked pull request, exact-head CI, a squash merge using GitHub's expected-head check, and an exact-merge-commit release. It never overwrites an existing tag or force-pushes a branch. Automatic merge requires the configured workflow and every observed pull-request workflow root for that head to finish successfully; intentional job skips inside a successful workflow do not fail the whole graph. The required CI workflow must run on `pull_request`. GitHub repository rules remain authoritative. GitHub's merge endpoint provides a head compare-and-swap, not a cross-provider transaction or an atomic base-branch comparison.

When an automatic Work item begins with a GitHub issue from the delivery repository, Camp uses its recorded title for the pull request and includes a reference to the issue. Camp uses a generated issue-number subject and frozen delivery details for its commit and automatic squash messages. The reference leaves the issue open for its own resolution.

Authenticated webhooks for the pipeline’s own exact PR creation and merge are recognized by the stored actor, repository, branch, head and frozen body; they do not trigger another automatic request. New comments, edits, changed heads and other actors remain independent source evidence.

Work displays normal CI and deployment waits. The delivery queue polls only due active deliveries. Base intervals are 30 seconds, with a one-hour deadline and at most 120 check observations. Worker leases stay internal. Changes to the observed state update the small Work projection. Originals and immutable receipts are available separately. A successful configured `push` deployment workflow must belong to the exact merge commit. When available, the confirmed GitHub Pages address becomes the result link. Work completes only after every authorized effect has a confirmed receipt.

Each visible effect has a durable intent before dispatch. A lost response or interrupted dispatch permits read-only reconciliation by exact branch/head, PR marker/account, merged PR, or tag/release marker. A due interrupted write is classified for receipt checking before applying expiry or changed project/rule grants to new writes. Absence from a bounded reader is not proof of non-delivery and never causes an automatic resend. **Check delivery** only reads the uncertain receipt and needs read access to the same repository/account. A successful check may resume remaining steps under the original authorization when the Work context and write grant are still current. Unresolved effects remain in **Needs me** even after the matter is stopped. Stopping withdraws unsent effects and preserves already dispatched outcomes.

Known failures offer **Resume delivery** after repair. This is a new recoverable Work command, not a silent retry: it preserves the accepted source/context, records the member's decision, and charges one additional remaining external action before retrying a visible effect. An uncertain action must be checked instead. New evidence, changed completion authority, expiry, disabled accounts or revoked connections cannot silently replace an accepted source or expand its grant. Repository renames/transfers and changed source baselines need explicit review.

Checked merge/release delivery can authorize up to three automatic repairs (the UI proposes one), shared across CI and approved review feedback. An explicitly reported exact-head source failure admits a new finite Collaboration Task within the original participants, current Agent/Runner permissions, cumulative Work allowance, original per-request ceilings, policy task/daily caps and expiry. The saved grant still governs cosmetic Agent edits. Camp attributes each repair decision to the system and cites bounded diagnostics. An immutable source ledger retains every accepted baseline/result/task. Camp overlays the accepted changes onto the previous known Camp branch head, then updates that branch and checks the same PR. The initial PR envelope and earlier receipts are retained as evidence. Camp checks the branch head and uses a fast-forward update to preserve unrelated history. The later merge uses GitHub's exact-head check and repository rules.

Use the required CI workflow to opt a source check into repair. Use a dedicated **Camp source check** job with one custom step of the same name. Standard GitHub setup, checkout and cleanup steps can run in that job. Emit one plain log line starting with `CAMP_SOURCE_REPAIR:` followed by a concrete diagnostic only when that test identifies a source defect. Camp verifies the failed step and reads bounded output from the exact job and workflow run attempt, then rechecks the current authorized head and attempt before admitting repair. The diagnostic is untrusted context under the existing scope. The [CI repair fixture](../scripts/fixtures/camp-ci-repair.yml) shows a source check that reports a missing release marker.

Missing, queued and rerunning workflows stay in the finite wait. Cancelled, timed-out, skipped or unclassified failures open **Needs me** with **Open workflow run** and **Check again**. Missing diagnostics and failures in other workflow roots also require inspection. A recorded generic CI failure from an older Camp version needs a current observation before repair. **Check again** starts with the same authorized PR or deployment commit and uses no visible-effect or model allowance for the observation. A newly observed eligible source failure can use the original remaining repair grant.

Review feedback is read only for active authorized deliveries. Only the latest submitted `CHANGES_REQUESTED` review from a frozen allowed numeric actor of the matching GitHub source policy, on the exact current head, can request repair. Current policy authority is checked again before admission and dispatch. Other review text is evidence, never authority; GitHub’s own required-review rules remain enforced. Known pending repository gates wait quietly within the same finite delivery deadline; changed/conflicting target branches require source review. This does not add general review-history polling or retroactive webhook processing.

Transient GitHub read failures wait quietly for at most three retries within the delivery deadline. GitHub rate-limit hints can extend the delay up to that deadline. The next observation starts after the indicated retry time or ends at the existing deadline. Exhaustion, changed scope, missing credentials and unconfirmed side effects retain distinct recovery causes. **Repair and continue** explicitly grants one additional repair within the remaining cumulative allowance and the hard three-repair ceiling. Changing project/rule authorization fences further rule-derived delivery. Uncertain effects still offer only **Check delivery**. Original files, partial drafts, charges and receipts survive every failed or withdrawn attempt.

Connection changes retain their stable operation ID after an uncertain response. **Check status** reads the personal receipt. **Cancel pending change** either recovers a concurrently saved connection or commits a tombstone that rejects a late original write. Credential text stays only in the mounted form; save or clear it before navigation. Disabling a connection withdraws further write authority while retaining its history and read-only receipt recovery.
