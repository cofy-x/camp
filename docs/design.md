# Platinum visual and interaction design

Camp uses compact gray controls, crisp bevels, striped active title bars, shared icons and overlapping windows, initially informed by [Platinum9](https://github.com/grassmunk/Platinum9). Readability, Unicode and usable keyboard/touch behavior guide adaptations. Change shared controls and tokens together when the visual direction evolves.

## Product principles

These principles apply to new features and refactors. The sections below define their current interactions; [architecture](architecture.md) owns authorization and state transitions.

- **Reduce attention and manual steps.** Work advances within an explicitly authorized policy and finite grant. Lead with progress, useful results and the person's required decision. Routine bookkeeping must not introduce another confirmation, self-review or delivery step for already authorized work.
- **Interrupt for current responsibility.** Needs me reflects unresolved judgments, assigned reviews and recoverable exceptions. Activity records observations; unread does not mean unresolved. Ordinary waiting and past failures do not automatically become new responsibilities.
- **Reuse the destination.** Work owns matters, Workspace owns discussion and Library owns files. Shortcuts open that existing owner. Add a desktop icon, screen or tab only for a distinct recurring user goal, not to expose another backend entity.
- **Keep the normal path small.** Show the current object and next useful action once. Put optional handoff, formal human approval, provenance and diagnostics behind a named action. Prefer a flat view or selector to nested disclosure trees. Optional review must not become a prerequisite for ordinary results.
- **Keep consequences visible.** Selected Agents, actual file access, finite allowance, shared/private draft scope, current errors and uncertain-write recovery remain visible where they affect a decision. A cleaner screen cannot silently expand authority or discard unfinished work.
- **Preserve the visual system.** Use existing Platinum controls, typography, spacing and state cues. Place location in the window title and commands in the toolbar; avoid duplicate names, decorative icons and one-off font sizes. A UI simplification does not imply a new visual theme.
- **Treat responsiveness as part of UX.** Primary content and actions must not wait for optional metadata, history or diagnostics. Preserve reading position, focus and drafts through live updates. Follow the [performance contract](performance.md) when implementing those reads.

## Content and information hierarchy

Lead with current facts and the next useful action. Use grouping, alignment and spacing to make relationships and actions clear. Add secondary labels and descriptions only when they provide information needed to choose, act or recover. Each sentence should support a decision, input or recovery step. When removing copy, first remove repetitions of headings, values and controls; do not replace them with another explanatory paragraph. Keep routine setup instructions and technical procedures in Diagnostics or the owning guide, while errors and consequential choices remain at their controls.

| Information | Placement |
| --- | --- |
| Current value, destination, recipients or work state | Beside its control/item |
| Required input, blocking capability, error and recovery | At the affected action/field |
| Shared publication, revocation or other decision-changing consequence | At the action or confirmation |
| Source explaining an externally locked field | Short label beside that field |
| Runtime provenance, detailed limits and previous observations | Named disclosure near the group |
| Repeated heading, action label or already visible status | Remove |

Keep labels concrete and vocabulary consistent. Empty states offer visible, editable starting points and enough explanation to choose; populated panels should not retain that tutorial. Tooltips supplement labels, never carry a required permission, consequence or recovery. Blocking errors remain outside disclosures.

Give each field and action a stable accessible name. Associate consequences, limits and errors with their controls so a keyboard user, screen reader or browser agent can discover them in the same place. Use the owning API and its receipts when automation needs to verify an identity, a transition or the result of a write.

Keep empty states compact and align their icons, text and actions as one group. Keep a command in its existing toolbar when that toolbar remains visible; do not repeat it in the empty pane. Use a quiet status row for unavailable optional Agent work, with one relevant setup destination. Room discussion remains usable without expanding a warning or reading setup instructions.

Distinguish configured from verified, private draft from shared version, captured from published, checks from tool activity, and completed work from human approval. A request allowance is not a billing cap. Simplification must preserve these facts and the user's unsaved input. Technical names belong in diagnostics when they do not help a product decision.

An ellipsis means further input/confirmation is required. **Ask agent…** prepares a cited draft requiring recipient selection and Send. Ordinary messages keep their reply or linked-work action visible; Ask agent, Follow up and Remember this share a persistent overflow menu rather than repeated action rows. Linked messages retain thread navigation in that menu. Overflow menus use a concise accessible name, visible focus, ArrowDown opening and Escape focus return; required actions never depend on hover.

## Windows, controls and narrow layouts

Use one title frame, optional compact toolbar, remaining content area and optional status bar. The frame names the current location or selected object and its application. Nested Workspace views retain their Room context. When a settings, editing, creation or import workflow owns the window, name it in the frame and restore the location on return. Give a dedicated settings view its own toolbar. Reusable forms keep a local heading when the enclosing frame leaves the workflow unnamed. Toolbars hold commands, filters and navigation controls. Show the subject of a task, review or document once across its detail views when it differs from the frame's location. Keep location selectors and selected navigation entries available. Wrap status text so save errors remain readable. Use distinct shared cues for active, inactive, pressed, selected, focused, default, disabled and error states.

The menu bar follows the active window. File owns generic desktop selection/open commands and names the selected app; Window/overview recover hidden windows. Dialogs contain focus and restore it on dismissal. Shared nonmodal Palettes keep anchoring and dismissal with the host: Escape/close restores toggle focus; outside dismissal preserves the destination's focus. The persistent Needs me toggle shows unresolved responsibilities, with a separate quiet indicator for unread Activity. Its Inbox Palette opens Needs me first; Activity retains the notification feed and marks a notification read only after draft-safe navigation succeeds. Reading never resolves a business item.

Camp's tent mark appears in the browser tab, on the startup and sign-in screens, in About This Desktop, and as the system menu button. [Tent artwork](../apps/dashboard/public/camp-tent.svg)

The Control Strip opens Workspace, Work and Library in one step. Workspace uses overlapping conversation bubbles, and Work uses a clipboard. Each shortcut uses its application icon and brings the existing window forward with its current view and draft. The active shortcut has an inset state, and the handle saves the strip's visibility preference. Appearance lives in View and Settings. Preference saves apply only the changed fields and return the current settings for the signed-in user. The menu bar announces Server reachability from its health read and shows text while connecting or offline. Write failures retain their own recovery controls.

### Reading and recovery

Folding a window pauses its reads while preserving its drafts, selection and reading position. Reopening revalidates the retained view. Optional application code loads inside its existing window; a failed download offers a local retry without reloading the desktop. Shared read lifecycles and notification handling follow the [performance contract](performance.md#reads-and-live-observations).

Preserve text selection, copy/paste, editing shortcuts and IME composition. Shading/hiding retains drafts and live work. Use the shared menu, Select, tabs, Radio and Progress rather than imitating them with feature-specific markup. Native wheel/touch scrolling remains usable even where host scrollbar artwork differs. Menus and dialogs stay inside visible bounds.

### Narrow windows

Adapt to application-window width through wrapping, stacking and scrolling. Narrow Settings/Agents/Runners replace sidebars with the shared pop-up. Narrow Workspace uses one Room identity/switcher with unread indicators and a separate action row. Long paths/titles wrap without widening the window. Narrow desktop mode keeps active-app identity and access to inactive windows.

Mouse and touch use the same compact visual control dimensions. Control Strip transparent hit regions can extend into the reserved bottom area. On narrow screens the Inbox button shows its action and count, giving both bottom controls room. Keep safe-area handling, close/return/save actions and keyboard focus reachable. Radio arrow keys move and select within the same native group, wrapping at both ends and skipping unavailable choices; Tab leaves the group. Avoid page-wide horizontal overflow. Wide document tables may have their own labelled, keyboard-accessible horizontal scroll region.

## Review checklist

Before adding a screen, tab or confirmation, identify its user goal and required action. Choose affected scenes, with broader coverage for shared desktop changes. For visible UI changes, review before/after screenshots of the actual implementation with synthetic data. Record source revisions, viewport, browser, device scale, content, window bounds and interaction state.

Embed before/after images directly in the PR, preferring GitHub image attachments. If the available tools cannot upload attachments, embed PNGs from a separate immutable image-only evidence commit and state their source revisions and synthetic-data provenance. Keep generated images out of the application source branch and private team data out of public evidence. CI artifacts retain supporting traces and reports; an archive link alone does not replace visible comparisons.

| Scene | Inspect |
| --- | --- |
| Attention and action cost | One clear primary action, no redundant labels/buttons or added routine approval, essential authority and recovery visible |
| Overlapping windows and menus | Active/inactive frames, layering, icons, menu bar and Control Strip |
| Controls/dialog/Palette | Pressed, selected, focus/default/disabled states, keyboard opening and dismissal |
| Changed app | Normal, loading/empty, long names, failed/uncertain writes and recovery |
| Narrow/short/resized windows | Reachable composer/actions, bounded scroll, no page overflow, focus-safe navigation |
| Reads and live updates | Primary content usable during related loading/failure, retained drafts/focus/history, affected [performance checks](performance.md#validation-and-evidence) |
| Discoverability | Required actions and their current context found by role, name and field description during keyboard and browser-agent use |
| DPR 1, fractional (e.g. 1.5), DPR 2 | Shared font roles, text wrapping, borders, title stripes, icons and Unicode fallbacks |

Typical review sizes are 1440 × 900 desktop and 390 × 844 touch; include smaller app bounds and zoom where relevant. Use actual keyboard, pointer and touch actions alongside screenshots: switch, resize/shade, open/dismiss, edit and recover. Compare copy as well as geometry, including a failed state when reducing detail. Use [contribution checks](../CONTRIBUTING.md#checks); visual fixtures, actual protocol tests, native isolation and real model runs establish different evidence.
